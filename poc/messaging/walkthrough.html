Control flow

Each agent receives only what its job needs.

Admission happens before model work. The planner sees the current message, three recent exchanges, and unresolved requests. The application executes bounded user-scoped queries and adds owned posts linked from those requests. The responder alone receives all current user memories.

1Query planner

Returns at most six structured queries. It cannot write SQL or see all memories.

2Responder

Returns the visible answer plus zero or more versioned post changes and a pending-candidate outcome.

3Memory

Creates, updates, or deletes durable preferences after publication. It does not store project facts.

4Addressing

Marks only directly answered or explicitly ignored prior requests. Deferrals stay open.

Proof boundaries

Observed success and deterministic failures are separate evidence.

The live run proves model behavior for these exact invented inputs. Scripted tests prove control-flow invariants that a happy-path live run cannot exercise safely.

Observed in the live run

Eight real calls completed

Planner, responder, memory, and addressing each ran exactly once per turn through the Google subscription adapter.

No unnecessary research

The responder declared only finish, search, fetch, and the fetched-body reader. Private evidence was sufficient, so none ran.

Semantic distinctions held

“Free” remained price; MIT remained license. PDF stayed planned, never shipped.

Parallel background order held

Both background start events preceded the first completion, and finalize followed both jobs in each turn.

Deterministic failure and replay checks

Rejected admission cannot abort ownership

Different text, cross-user collision, identical concurrent delivery, and another same-user turn all return failed admission receipts while the legitimate turn stays locked.

Successful jobs do not rerun

A retry after memory failure made one new memory call and zero new addressing calls. The answer and post diff remained singletons.

Stale retry cannot restore old intent

After a newer turn changed “detailed” to “concise,” retrying the older failed memory job was rejected before a model call.

Bounded recovery fails visibly

Two background attempts are allowed. Terminal failure releases the send lock; an exhausted or stale retry returns an explicit error.

Atomic ownership checks

Version conflict and foreign ownership reject the whole post batch without partial writes.

Research ceiling

A ninth responder research observation fails closed and publishes no answer.

Planned production boundary

Transactional database admission

Replace the fixture maps with a unique per-user active-turn constraint, versioned writes, scoped queries, and durable idempotency receipts.

Durable background queue

Persist memory and addressing jobs, attempt counters, terminal failure, progress events, and the stale-turn sequence check across process restarts.

Prompt 1 · Query planner 
# Query planner

Resolve references in the current user message using only the supplied last three completed exchanges and pending assistant requests. Cover every named or affected project, not only the first one. Return zero or more simple search queries over posts, user messages, or assistant messages. The application already retrieves owned posts linked from pending requests, so do not duplicate those lookups; query every other affected project. Use concrete terms from the conversation. Keep each limit small. Do not request all memories or invent SQL. The application owns scope, parameters, cutoffs, and query execution.
Prompt 2 · Responder 
# Responder

Answer the authenticated user in plain, concise, factual language. Use the current message, bounded query results, all supplied memories, all unaddressed assistant requests, and the last three completed exchanges. Classify the answer and its outbound intent explicitly. Return zero or more owned-post changes with exact expected versions and evidence references. Never write storage directly. Publish useful supported changes immediately without an approval step. If evidence is insufficient, ask one targeted question and invent no post. A useful partial update may be applied while asking one meaningful remaining question. Preserve stated preferences as preferences, not product facts. Price and license are separate facts: “free” does not state a license. Keep planned or future features explicitly planned; never promote them to current capabilities. Memory and request-addressing tasks run after this answer becomes visible, so acknowledge preference and request intent without claiming that a preference was saved, updated, deleted, or that a request was closed.

For a pending candidate, choose none, publish, or clarify. Publish only when the user resolves the missing fact and cite the candidate plus supporting message or request; the application assigns the post ID and records the candidate-to-post association. Do not repeat a supplied outstanding request, ask a generic follow-up, or nag after a deferral. Existing unresolved requests remain visible without appearing again in the answer. Native web search and page reading are available when current public facts are necessary; cite only observed fetched/search evidence. You have at most eight research tool calls. After `read_url_content`, call `readFetchedPage` with the same URL because the native receipt is not the page body. Stop research once the supplied private evidence resolves the task.
Prompt 3 · Memory 
# Memory

Compare the user message and assistant answer with every supplied user memory. Return idempotent create, update, or delete operations for durable user preferences only. Replace conflicting preferences intelligently. Delete a preference when the user retracts it. Do not store transient project facts, assistant guesses, or a duplicate of an existing preference. There is no archive or restore operation.
Prompt 4 · Addressing 
# Addressing

Review the supplied snapshot of previously unaddressed assistant questions, requests, and suggestions against this user message and assistant answer. Resolve only requests directly answered or explicitly ignored now, and give a short evidence-based reason. Unrelated new information, partial answers, and deferrals remain open. Do not address a new request in the current assistant answer because it is not in the snapshot.
