Exactly how pulling and batching work · proposed defaults
  1. One reader owns a lease per group. Use the stable Telegram group/person IDs, not usernames.
  2. First run: freeze a start time seven days ago and the current highest message ID. Read oldest first with reverse: true, offsetDate: start and maxId: upper + 1. After the first stored page, resume with minId: lastStoredId.
  3. Later runs: freeze a fresh upper ID and use reverse: true, minId: cursor, maxId: upper + 1. Read at most 100 new messages per batch, oldest first. IDs need not be consecutive.
  4. Each page transaction upserts messages by (groupId, messageId), advances the stored cursor and inserts a unique batch outbox job. A crash before commit repeats the page; after commit the job is already durable.
  5. The outbox worker launches TelegramBatch under the stable batch ID. Fetching and AI processing have separate status; selection failure never discards the saved messages.
  6. Add 20 earlier messages as context, plus referenced replies and album members. Only new messages trigger candidates. Keep full raw text; oversized context is split or deferred explicitly, never silently cut.
  7. Poll every 60 seconds; honor Telegram’s requested flood-wait delay. Begin with two concurrent model calls globally and one publisher per author. These are tunable defaults, not product decisions.
  8. The cursor catches new messages, not edits or deletions. Reconcile the recent week separately before claiming edit/delete support. Media-only posts need a later media-reading adapter; retain them as pending, not discarded.

GramJS documents reversed offsets and exclusive ID bounds in its message iterator source. Validate these boundaries with a disposable read-only group before connecting the real reader.

Tool inputs, results and permissions
ToolInput → output
searchWebQuery → up to five public pages with URL, title and text.
readPageURL → one public page with its final URL, title and text.
searchMessagesQuery → up to 20 stored Telegram messages in the candidate’s group, before the batch cutoff.
readMessagesUp to 20 IDs → matching messages within the same group and cutoff.
searchPostsQuery → up to ten current posts owned by the candidate’s author, including versions.

Eight tool calls per task in this reference. Application code supplies the scope and validates both arguments and results. No model has a database write, shell, filesystem or Telegram-send tool. Web fetches reject private addresses, including redirects. See all contracts and the actual allowlist enforcement.

Progress without guesswork

Answer published · finishing your turnMemory: running · Requests: complete

Show queued, running, complete, retrying or failed per task. Keep the answer and its diff visible while the last two tasks run. Enable sending only after their writes finish. A failed task offers retry without losing your draft or repeating completed work.

Progress comes from persisted task events, not invented percentages or the model’s private reasoning. Reopening Agent restores the same state. The local UI illustrates progress with an explicitly labelled example.

Decisions recorded Confirmed

  • One Agent conversation per user; structured tasks and explicit context instead of replaying the full transcript.
  • The planner also sees recent messages. The answer sees all memories, all unaddressed messages and the last three exchanges.
  • Post changes apply automatically, with actual diffs.
  • Only explicit questions, requests and suggestions seeking a response are unaddressed. The resolver can mark them answered or ignored.
  • The memory agent sees current memories and decides what to create, replace or remove.
  • Research first; ask when meaningful uncertainty remains. The exact information threshold still needs refinement.
  • Block the next message until the whole workflow finishes, while exposing each task’s progress.
Application boundaries · proposed implementation

Use one PostgreSQL database with separate tables for user messages, assistant messages, memories and posts, plus raw Telegram messages, candidates, source links, jobs and progress. The planned pg-boss queue admits jobs and schedules retries. Smithers owns workflow execution state; application transactions own published state. Give retry timing one owner to avoid multiplying attempts.

Private records are scoped by the authenticated user. Post edits recheck live ownership and versions. Memory operations recheck the snapshot version. A conflict reruns the affected task with fresh data.

Candidate publication uses an author lock shared with chat, a unique candidate/revision receipt and source/project identity checks. Same-author writes serialize. Public URLs and semantic similarity help matching, but neither alone guarantees that two posts describe the same project.

Retries use bounded backoff and fresh attempt IDs, retaining stable business keys. The production host must persist admission, task status and retry jobs. The reference’s in-memory tests do not implement or prove those database contracts.

Three things to refine

  1. What deserves a post? The draft prompt selects concrete work and meaningful updates, and skips news, chatter and vague plans. Review it against real group messages before treating this as a settled policy.
  2. When to ask? The draft publishes what is supported, asks one focused question when useful, and holds a candidate only when its basic identity or purpose is unclear. Question frequency and backlog limits remain open.
  3. Duplicate identity. Exact known sources are easy to match. Renames, multiple links and the same project across groups need a small set of real examples to settle create-versus-update behavior.
