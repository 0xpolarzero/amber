What we have decided Confirmed

  • Each user has one conversation with Amber, across multiple posts.
  • Amber can ask questions. Messages awaiting an answer are highlighted as unaddressed.
  • Responses follow a fixed workflow, to be implemented with Smithers later.
  • User messages, assistant answers, user memories and posts are stored independently. The displayed conversation is not the model’s full input.
  • Each user message triggers the four model tasks below. Every task returns structured output.
  • Amber applies post changes and shows their diffs. No approval step.
  • Preferences are remembered across posts. Users can inspect, edit and forget them.

Resolve messages · model task

Input: user message + published answer + unaddressed messages. Output: IDs of messages now answered.

Tasks 03 and 04 run in parallel after publication. The UI does not wait for them to display the answer. Older conversation enters the answer task only through retrieval.

BoundaryReference behavior
StorageFour application tables in one PostgreSQL database. Smithers execution state is separate from application data.
SearchStructured collection + search text, never generated SQL. Application code limits results and enforces access. The query planner gets only the current message.
Recent contextThe last three completed user/assistant pairs before the current message. A sequence cutoff excludes later messages and the current turn itself.
OutstandingOnly messages that require a reply. The answer task returns needsReply; the resolution task returns existing candidate IDs. Partial answers remain outstanding.
PublicationOne transaction saves the answer, supported edits, diffs and pending maintenance records. Ownership and current versions are checked in application code.
Background failureRetain the published answer. Retry the failed branch from its saved inputs; its successful sibling remains complete.
Memory writesStore candidate preferences with user-message evidence. Reconcile duplicates and conflicts against current memory; protect preferences the user edited or forgot.

Decisions still open

  1. Overlapping turns: does the next message wait for background memory and resolution, or start immediately with the last committed state? Waiting improves consistency but can delay the next answer.
  2. What needs an answer: only explicit questions, or also requests and suggestions? What counts as addressed when the user answers only part?
  3. Ambiguous messages: “yes” gives the query planner no subject. The answer task has recent context; should retrieval also receive it?
  4. Memory conflicts: when does a new preference replace an old one, and can an explicit request restore a forgotten preference?
  5. Proactive questions: what triggers Amber to send a message about a post, and how many outstanding questions are acceptable?

Reference and verification

workflow.ts contains the schemas, four task prompts, Smithers graph, application action contracts and handler wiring. The database and subscription model adapters are deliberately unimplemented.

The file targets the current Smithers 1.0 source at 6d40cbc, using Effect 4.0.0-rc.112. The installed CLI reports 0.35.0; npm returned 404 for the new packages during research. No CLI upgrade or live model run was performed.

What has been checked

Typechecked against the pinned upstream source. The real in-memory Smithers engine verifies exact context, publication order, parallel background tasks, completed-run reuse, malformed output rejection and an independent memory failure. Pure checks reject unknown, foreign, stale and duplicate post changes.

These checks do not prove production crash recovery, database transactions, cross-process callback identity, token limits or Gemini subscription access. The host must supply stable deployment identities and durable adapters before integration.

Tests live beside the reference and run through test:agent-reference with SMITHERS_SOURCE pointing to the pinned checkout. No Smithers dependency was added to the web app.
